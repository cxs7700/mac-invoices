Seven directions for how Rent Ops looks and behaves on a phone — the landlord's list and filters, the vendor's field submission, the app shell, and the design system underneath all three. This app is further along than its docs suggest: a mobile drawer, camera capture, a full light/dark token system and an installable per-vendor PWA already shipped. So these ideas are aimed at what is actually broken, and two of them fix live defects found during grounding.

Grounding Context

Codebase Context

  • npm-workspaces monorepo: apps/web (React 19, rolldown-vite, React Router 7, RHF, TanStack Query, Tailwind v4, i18next EN/ZH), apps/api (Fastify 5 + Prisma), packages/shared (Zod).
  • ~7,700 lines of TSX/TS across 13 pages and ~30 components.
  • Two users with opposite contexts: a landlord reviewing and paying at a desk, and vendors submitting invoices with photos from a phone in the field via a no-login HMAC link.

Already Shipped

  • Mobile top bar + slide-out drawer; Sidebar is hidden md:flex.
  • capture="environment" in PhotoAttach — camera vs library is solved.
  • The iOS zoom fix (text-base md:text-sm) in lib/fieldClass.ts.
  • Full light-dark() token system with status and tone pairs.
  • Vendor page is an installable PWA: runtime per-vendor manifest, scoped service worker, viewport-fit=cover, safe-area padding.

Measured Gaps

  • Zero responsive utilities in InvoiceList.tsx (306 lines), InvoiceTable.tsx, Settings.tsx, InvoiceForm.tsx and 14 more components.
  • The only UI primitives are @radix-ui/react-slot and one button.tsx. No dialog, drawer, popover, toast or select — every overlay is hand-rolled.
  • The 375px overflow audit was scoped in a prior spec but never finished; two more overflows were found after the fact.

Constraints Ideas Must Respect

  • Colors route through a light-dark() token — no raw hex, no one-off dark:.
  • Filter/sort/page state lives in the URL; list and dashboard share one DateRangePicker and one parseListParams.
  • All copy is bilingual EN/ZH; new strings are added twice.
  • New dependencies need gz-weight + license justification and code-splitting.
  • The service worker stays scoped to /submit; the landlord app is deliberately never cached.
  • House stance on mobile work: concrete defects, not a speculative sweep.
Scope boundary

A separate ideation run the same day owns reporting content — aging, period-over-period, per-vendor rollups, CSV and Schedule E. Nothing here proposes a new metric or export format; these ideas govern how figures are laid out, navigated and touched.

Topic Axes

  1. Landlord list & table landlord-list-table — the invoice list, table, filter bar, pagination and dashboard stat/chart surfaces on small screens.

1

Two renderers, one column manifest

landlord-list-table Confidence 90% Complexity Medium
Description

The landlord's main screen is a nine-column table inside a horizontal scroller, and neither InvoiceList.tsx (306 lines) nor InvoiceTable.tsx contains a single responsive utility. Rather than hand-writing a second mobile layout that drifts from the first, extract a column manifest — key, label, priority, alignment, cell renderer — and feed it to two presenters: the existing <table> at md: and up, and a stacked card list below it, where the invoice number is the card header and the remaining fields become label/value pairs.

The manifest is what makes this affordable. One place defines what a column is, so currency formatting, status tone and truncation are written once and the two views cannot disagree.

Basis

direct: InvoiceTable.tsx:42 is <div data-rscroll className="overflow-x-auto rounded-lg border border-border bg-card">, and lines 99–100 truncate the two most descriptive columns with max-w-xs truncate — so the fields a landlord scans for are clipped and parked off-screen. Verified: nine columns, zero sm:/md:/lg: prefixes in the file.

external: The card/list transform is the dominant 2025–26 pattern for dense tables on mobile; horizontal scroll is the documented weaker alternative (Setproduct; Medium/Bootcamp).

Rationale

Horizontal scroll is the one mobile table strategy that hides the scanned fields rather than reflowing them, and this screen picked it by default rather than by choice — there is no responsive code here at all. This is also the natural home for three smaller verified defects: the unfinished 375px pass, the SyncBadge long/short label convention (cards have no column header to give "No" its meaning), and Dashboard.tsx:116's grid gap-4 sm:grid-cols-4, which below 640px stacks four full-width tiles and pushes the chart off the fold.

There is a free acceptance check sitting in the file already: data-rscroll appears exactly once in the whole codebase and nothing reads it. Give it meaning as an opt-in "allowed to scroll sideways" marker and a jsdom render at 375px can assert nothing else overflows — turning a hand audit that has already been missed twice into a test.

Downsides

A manifest is indirection: contributors must learn it before adding a column, and very custom cells fight it. Card lists also lose column-to-column comparison, which is the one thing tables are genuinely better at — so the md: table has to stay, not be replaced.

2

A Field primitive with a guard that fails the build

design-system-drift Confidence 95% Complexity Medium
Description

Four components each hand-roll their own input class string instead of importing the shared one. Collapse them into a real <Field> component — label, input, error slot — rather than a bare string constant, so a new form field arrives with correct mobile sizing, error wiring and token colors by default. Then add a guard: an ESLint no-restricted-syntax rule (or a test) banning the literal border-input outside lib/fieldClass.ts.

Basis

direct: This is a live bug, verified twice. Settings.tsx:23 reads const inputClass = 'mt-1 w-full rounded-md border border-input bg-background px-3 py-2 text-sm' — it omits text-base. fieldClass.ts documents in-file that text-base md:text-sm is "load-bearing, not cosmetic": Mobile Safari zooms any focused input under 16px and never zooms back out. Settings is where a landlord changes their email and password, on a phone.

Rationale

The team already found this bug, fixed it, and wrote down why — and it came back somewhere nobody looked, because the fix lives in a string that two of six call sites import. That is the signature of a missing abstraction, not a missing code review. The guard matters more than the refactor: without it the same regression returns the next time someone types out an input by hand, and this repo has concurrent sessions committing to main.

The same move retires the neighbouring drift the dossier counted — 18+ card containers across five padding values with no name — by giving the card recipe two or three named densities mapped to the documented 8/12/16/22 rhythm.

Downsides

A lint rule banning a utility class is unusual and will annoy someone writing a genuinely one-off input; it needs a documented escape hatch. Migrating six call sites also touches forms that currently have no test coverage.

3

A submission that survives the field

vendor-submit Confidence 92% Complexity High
Description

Three changes that only make sense together, because each one makes the next cheaper. Compress before upload: downscale to ~2000px on the long edge and re-encode as JPEG in a canvas before the PUT, which also normalizes HEIC into something every downstream surface can render. Persist the draft: write the whole form — items, date, property, notes, and the already-uploaded blob URLs — to storage keyed by the link token, and restore it on return. Then retry: an upload that fails gets exponential backoff rather than a dead end, and a failed photo stays queued instead of being discarded.

Basis

direct: useImageUpload.ts accepts up to 10 MB and sends the raw file with no compression. VendorSubmit.tsx:82–89 holds every field in plain useState with no persistence, and resetForm/startNew wipe it. useSubmission.ts is a bare mutation with no retry or backoff. Separately, PhotoAttach.tsx:74,83 puts disabled={disabled || uploading} on both capture buttons, so a vendor cannot even line up the next shot while one is in flight.

external: Retry-with-backoff and durable local drafts — not mere offline storage — are what actually survive a dropped signal in field-worker intake (Supportbench; dev.to). Canvas compression between capture and upload is the standard PWA document-scanner step (Dynamsoft).

Rationale

This app invites the worst case: the submission page is installable to a vendor's home screen, so they open it exactly where connectivity is poorest. Today a phone call, a backgrounded tab or a basement costs them everything they typed and every megabyte they already pushed over LTE — silently, with no error and no recovery but retyping.

Ordering matters. Compression shrinks a typical phone photo by roughly an order of magnitude, which shortens the window in which failure happens at all and makes a retry cheap enough to be worth attempting. Draft persistence is the substrate the retry resumes from — building the queue first means rebuilding it later. It also lands on the one route where the service worker is already scoped, so none of it threatens the rule that the landlord app is never cached. As a bonus it cuts Blob storage spend on 10 MB originals that render as thumbnails.

Downsides

The largest item here by far. Canvas re-encoding loses EXIF orientation unless handled explicitly and degrades a receipt photo that may later be evidence in a dispute — the compression target needs care. Persisting blob URLs means reasoning about expiry, and a restored draft that silently references a dead upload is worse than no draft. Storage also needs a clearing rule so a shared phone does not leak one job into the next.

4

An overlay primitive that costs zero bytes

forms-feedback-a11y Confidence 88% Complexity Medium
Description

Three overlays are hand-rolled in this app — the image lightbox, the notifications panel, and the mobile nav drawer — and none of them traps focus, restores focus, marks the background inert, or closes on Escape. Build one internal Overlay/Sheet on the browser's own <dialog showModal()> (plus the popover attribute where non-modal) and adopt it in all three.

Basis

direct: The nav drawer declares role="dialog" aria-modal="true" at AppShell.tsx:112–113 but the component contains no Escape handler and no focus management at all — only a backdrop onClick. Verified by grep: Escape appears in VendorCombobox, AddressAutocomplete and InvoiceList, never in AppShell. Separately, NotificationsBell.tsx:33–53 measures getBoundingClientRect() and attaches resize and capturing scroll listeners to keep a 320px panel from drifting.

reasoned: The dependency constraint asks for gz-weight and license justification for new packages. <dialog> and CSS anchor positioning are already in the browser, so this is the one path that satisfies both the "no primitives exist" drift finding and the a11y gap at a bundle cost of zero.

Rationale

Announcing aria-modal="true" while leaving focus loose is worse than not announcing it: a screen-reader user is told the rest of the page is inert when it is not, and a keyboard user has no way out of the drawer. Adopting the platform element also deletes code — the whole reposition-on-scroll dance in NotificationsBell exists to reimplement what anchor positioning does natively.

Worth noting what this idea is not: an earlier candidate claimed the app had only two live regions and needed a whole announcer layer. That was wrong — there are four aria-live regions, 32 role="alert" and 7 role="status" usages, so error announcement is already broad. The real accessibility gap is focus and dismissal, not announcement.

Downsides

<dialog> brings its own quirks — backdrop styling, scroll locking on iOS, and top-layer stacking that can surprise. Anchor positioning is the newest surface here and needs a fallback path. Three adoptions in one change also risks a visual regression in the lightbox, which is currently the one deliberately theme-invariant surface in the app.

5

Capture first, classify never

vendor-submit Confidence 85% Complexity Low
Description

Two small reorderings of the vendor flow. Move capture to the top of the form, so the first thing the page asks for is the photo rather than the sixth. And infer the photo's type from the button that was tapped: replace one generic "Add photo" with two labelled entry points ("Receipt / cash", "Parts") that pre-set the type, demoting the per-photo dropdown to a correction affordance instead of a required step.

Basis

direct: InvoiceFields.tsx renders items → date → property → category → notes → parts, and the photo block lives outside it, rendered afterwards at VendorSubmit.tsx:227–292. canSubmit at VendorSubmit.tsx:124 is !!invoiceDate && !!propertyId && filledItems.length > 0 — photos gate nothing and come last. Type is set only through a per-photo <select> at VendorSubmit.tsx:248–259, defaulting to 'OTHER'.

external: Jobber's field-service UX is cited as best-in-class for a one continuous flow with zero training; Expensify opens on capture and confirms quality before anything else is asked (Jobber; Expensify).

Rationale

The receipt is the one artifact in this flow that cannot be reconstructed later — the vendor is holding it, in a driveway, and it is the thing most likely to be lost. Everything else can be typed from memory that evening. Asking for it last inverts perishability, and asking for it after six fields means an abandoned form loses the photo too.

The type dropdown is pure classification overhead at the worst moment: ten photos currently means ten dropdown interactions on a phone, one-handed. The button tapped already carries the answer, and because the enum and the correction UI both already exist, this costs no schema change.

Downsides

Two capture buttons where there was one adds header width on the narrowest screens, and the pairing only holds while the type enum stays small — a fourth type forces a rethink. Leading with the camera may also read as "a photo is required" when it deliberately is not, so the copy has to carry that, in both languages.

6

Give page actions their own slot

shell-nav-pwa Confidence 82% Complexity Medium
Description

Two separate 375px overflow comments exist in this codebase, and they are the same problem wearing different clothes: actions are placed by who owns the chrome rather than by what the page needs. Introduce a PageActions slot — a right-aligned row at md: and up, a bottom-anchored bar below it that respects env(safe-area-inset-bottom) — and write down a header budget naming what may live in the top bar and what may not. Evict Log out to the drawer as the first application of that budget.

Basis

direct: AppShell.tsx:93–95 carries the comment "five controls do not fit across 375px, and the squeeze clipped its own last segment" — the theme switcher was already exiled once. Yet the slot it protects still holds Log out, rendered at AppShell.tsx:99–105 as className="shrink-0 text-xs text-muted-foreground hover:text-foreground" with no min-h or min-w. InvoiceList.tsx:158–159 separately records that its three header actions total ~395px and pushed "New invoice" off a 375px screen.

external: WCAG 2.5.8 sets a 24×24 CSS px floor for targets, with 44×44 the platform norm; a bare text-xs link fails even the AA minimum (TestParty).

Rationale

A once-a-session destructive action is occupying contested space a thumb-width from the notifications bell, at a tap size below the accessibility floor — that is both a capacity problem and a misfire hazard. Meanwhile InvoiceList's current mitigation is flex-wrap, which changes where things wrap without making the primary action reachable.

Writing the budget down is the part that compounds. The header has already been re-arranged once under space pressure; a named rule — identity, attention, escape hatch, nothing else — turns an undocumented constraint into one the next feature can be checked against. A cheap companion: the drawer is absolute inset-y-0 flex flex-col with links top-packed and its lower half empty, so pushing them to the bottom puts every nav tap in the thumb zone for two words of CSS.

Downsides

A bottom action bar competes with iOS Safari's own chrome and can feel cramped on short screens; it also needs care not to obscure the last row of a list. Moving Log out makes signing out slower to reach, which some users will read as a regression, and the budget only holds if someone enforces it.

7

Measure the box the component is actually in

design-system-drift Confidence 78% Complexity Medium
Description

Every responsive decision in this app is a viewport breakpoint, but the landlord layout has a fixed 224px sidebar, so a component styled for "640px and up" may actually be laid out in far less. Adopt the split Tailwind v4 makes available: viewport queries decide page layout (sidebar versus drawer), container queries decide component internals (table versus cards, stat columns, chart label density). Container queries are core Tailwind v4 — no new dependency.

Basis

direct: Sidebar.tsx:19 is hidden md:flex with w-56 (224px). Dashboard.tsx:116 is grid gap-4 sm:grid-cols-4 — so at a 640px viewport the stat grid claims four columns while the content box is roughly 416px. The same mismatch explains SpendTrendChart.tsx:76, whose month labels are pinned at text-[10px] and which already thins labels adaptively rather than shrinking type further.

external: Viewport-for-page, container-for-component is the recommended pattern precisely for nested sidebar layouts (shadcn Tailwind v4 docs; Kickstage).

Rationale

This reframes a recurring bug class as a systematic mismatch rather than a run of individual misses — and the record supports that reading: the 375px audit was performed and still left two overflows to be found afterwards. No amount of care fixes a breakpoint that is measuring the wrong box. The sidebar is also collapsible, which makes the mismatch dynamic: no single viewport breakpoint can be correct for both states, so the current approach cannot be made right by tuning the numbers.

It also unblocks idea 1 honestly. "Cards below md:" is the same viewport assumption in new clothes; what the card view actually wants to know is how wide its own container is.

Downsides

Container queries need an explicit @container ancestor, so adoption is not a find-and-replace — get the containment root wrong and rules silently never match, which is harder to debug than a wrong breakpoint. Mixing both systems during migration is genuinely confusing, and it needs a written rule about which query type owns which decision or the codebase ends up with both everywhere.
