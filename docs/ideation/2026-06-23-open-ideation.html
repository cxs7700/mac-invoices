1

Tax-line categories that do real work → Schedule E + 1099 reporting

Confidence 85% Complexity Medium direct + external reporting · landlord JTBD

Description. Today category is a flat display enum (MAINTENANCE / REPAIRS / UTILITIES / SUPPLIES / LABOR / OTHER) that maps to nothing. Re-cast it as an IRS Schedule E tax-line identity, and surface the one decision that actually matters at capture/approve time: repair (deductible this year) vs. capital improvement (depreciated 27.5 yr). Then add two reports that fall straight out of data you already hold — a year-end per-tax-line summary, and a per-vendor annual spend rollup that flags any contractor paid over $600 for 1099-NEC. No schema change beyond a mapping and one decision field.

Basis · direct + external
packages/shared/src/schemas/invoice.ts:4-11 — InvoiceCategory is a flat z.enum of display labels with no tax mapping (verified). External: IRS Schedule E treats category as a tax-line identifier; repair-vs-improvement is the most consequential call. Buildium/AppFolio auto-generate 1099-NEC for vendors paid >$600/yr. The /stats groupBy primitive already exists to extend with _sum:{amount}.
Rationale

Grounding is blunt that Mac Invoices' real gap is the reporting / export layer, not CRUD. The whole reason Google Sheets export exists is the accountant handoff — yet the app throws away the one classification that makes that handoff filing-ready. This converts data already captured (date, vendor, amount, description) into the landlord's actual year-end deliverable.

Downsides

The repair-vs-improvement judgment is genuinely hard and you don't want to give tax advice — frame it as a hint with an "ask your accountant" escape hatch. A category remap touches existing 158 seeded rows (a backfill migration). 1099 thresholds are calendar-year and per-TIN, so "vendor" needs to be a stable identity, not a free-text string (nudges toward a vendor entity later).

Convergence: found independently by 5 of 6 frames (pain, inversion, assumption-breaking, cross-domain, constraint-flip) — the single most-agreed direction in the run.
2

InvoiceEvent: an append-only ledger that makes history real

Confidence 90% Complexity Medium direct foundation · leverage

Description. Add an InvoiceEvent table (type, field, oldValue, newValue, actorId, ts, invoiceId) written inside the same transaction as every create, edit, status transition, and export-stamp. Current invoice state stays the materialized row (the "HEAD"); the ledger is the log of deltas. This one table is the substrate beneath at least four features that are currently faked, deferred, or invisible.

Basis · direct
apps/web/src/components/InvoiceTimeline.tsx:7 literally comments "A data-backed status progression (no fabricated 'Viewed' step)" and derives nodes from current fields (if (invoice.status === 'PAID')) — proving the timeline reconstructs history because none is stored (verified). updateInvoice at handlers.ts:212 mutates in place with no event capture. External: git commit-log framing; medical 7-yr tombstone ≈ IRS retention.
Rationale

A two-party approval workflow over money needs provenance for disputes and IRS retention — and the timeline component is already a surface lying about its own data (a Paid invoice that was once Disputed shows no dispute). Reframing now, before more status logic accretes, is cheap; later it's a migration over years of records. This is the highest-leverage move in the set: it pays for audit, honest history, sync-as-event, and the activity feed at once.

Downsides

Every write path must now emit an event in-transaction — a discipline that's easy to forget without a single choke-point (pairs naturally with idea 4's transition handler). Event volume grows faster than invoices; needs an index and a retention story of its own. Doesn't replace the current row — it's additive, so there's a "which is truth" rule to document (HEAD = the row, ledger = how it got there).

Convergence: found by 4 of 6 frames (assumption-breaking, leverage, cross-domain, constraint-flip), each arriving via a different door — audit, git, accounting journal, "never delete."
3

Photo-as-source: presigned upload → OCR → draft invoice

Confidence 80% Complexity High direct + external missing capability · the namesake feature

Description. The InvoiceImage model (with ImageType cash/parts/check) is fully designed and completely unused; the create form ships a dead "Scan a receipt — Soon" tile. Wire the real pipeline behind the existing mockable, error-sanitizing integration seam: phone camera → presigned R2/S3 upload → OCR API (Veryfi / Document AI / Textract free tier) → auto-populated PENDING draft → landlord review. Manual entry becomes the exception path. The same photo simultaneously satisfies the core stated requirement (contractors + landlord viewing cash/parts/check proof).

Basis · direct + external
schema.prisma has InvoiceImage + ImageType (CASH/PARTS/CHECK/OTHER) + @@index([invoiceId]) with zero handlers anywhere in apps/api/src (verified); the dead tile lives at apps/web/src/pages/InvoiceNew.tsx:38. The seam to copy is proven at apps/api/src/integrations/sheets.ts (retry/backoff + error sanitization). External: practical path is an OCR API, not in-house; phone-camera → auto-populate → review is the established pattern.
Rationale

This is the feature the product was named around, and the data-entry tax — typing an invoice off a paper receipt — is the single most manual moment in the product, borne by the party (the contractor) least motivated to do it carefully. It's also the fleet-dispatch "photo-proof before approval" analogy made literal. A cheap companion ships alongside for near-zero cost: a duplicate warning when the same vendor + amount appears within an N-day window (the [userId, invoiceDate] index already exists).

Downsides

Highest complexity in the set: a new storage dependency (R2/S3), a paid OCR vendor, and presigned-URL security all at once. OCR accuracy on crumpled field receipts is uneven — the review step is non-negotiable, not a nicety. Needs the mobile nav drawer to exist first (the app is currently hidden md:flex — desktop only), or the field-capture half has nowhere to live.

Convergence: 4 of 6 frames; folds in the mobile-drawer, offline-capture, and duplicate-detection ideas as companions.
4

Approval as a gated transition engine (fix the dead APPROVED state)

Confidence 85% Complexity Medium direct workflow · core identity

Description. APPROVED exists in the enum, the StatusCounts strip, and the overdue logic — but there is no "Mark Approved" button, so a landlord can only jump PENDING → PAID and erase the approval record. Rather than bolt on one button, replace the ad-hoc per-button mutations with a single declarative transition map ({from → allowed[to]}) behind one POST /api/invoices/:id/transitions handler — and let transitions carry evidence gates (e.g. → APPROVED may require an attached photo). Adding APPROVED, and every future Buildium-style state, becomes a map row plus a button.

Basis · direct
InvoiceStatus in schema.prisma contains APPROVED; InvoiceDetail.tsx wires only Mark Paid / Dispute-Reject / Delete — no Approve action (verified). The codebase already favors exhaustive typed maps (sortClause: Record<InvoiceSortField,…> "so a new sort field is a compile error here"), so a transition map fits the existing grain.

Rationale

The product's one-line identity is "landlord approves contractor invoices" — and right now the landlord can't click approve, so the app silently asks them to lie about the lifecycle. The transition-engine framing turns the next eight property-management states (Coding required, Scheduled, Reconciled…) into data rows instead of bespoke endpoints, and gives ideas 2 and 7 their natural hook (every transition emits an event; every actor has a "next owner").

Downsides

A full state machine is more than the one-line fix the bug strictly needs — there's a real "just ship the button" counter-argument if the richer lifecycle never materializes. Evidence gates can trap users (an approval blocked because a photo upload failed) — gates need an override path. Allowed-transition rules must be exhaustively specified or you trade a missing button for a confusing 409.

Convergence: 4 of 6 frames (pain, inversion, assumption-breaking, leverage); the leverage frame contributed the engine framing, cross-domain the checklist gate.
5

Harden the hot paths before the portal multiplies writers

Confidence 90% Complexity Medium direct reliability · correctness

Description. Three correctness bugs on the core write/read paths, fixable as one focused pass because they share a root ("stop scanning / stop last-write-wins"): (1) replace the full-table-scan invoice numbering with a Postgres sequence; (2) add optimistic concurrency (updatedAt in the updateMany where-clause → stale edit returns 409, not a silent clobber); (3) close the at-least-once Sheets export's duplicate-row window with an idempotency key. Each rides an idiom the codebase already trusts.

Basis · direct
handlers.ts:26 — prisma.invoice.findMany({ select: { invoiceNumber: true } }) loads every row on every CREATE then maxes in JS; a P2002 retry loop (lines 35–84) is a band-aid over the resulting race (verified). handlers.ts:212 — updateMany({where:{id,userId},data}) is last-write-wins, no version check. sheets.ts:272 documents at-least-once delivery with a duplicate window keyed on the id column; idempotency dedupe is explicitly deferred (DEC-021).
Rationale

These are latent correctness bugs, not just perf: the moment two contractors hit "submit" in the same second (the entire point of idea 7's portal), invoice numbering collides and the retry loop papers over a race a sequence would prevent for free; two browser tabs editing one invoice silently overwrite an amount; and a dropped export ack duplicates rows in the tax sheet. Fixing them now is cheap and respects the binding export-only constraint (DEC-001); fixing them after the portal ships is a production incident. It's the de-risking layer under idea 7.

Downsides

A Postgres sequence changes how invoice numbers are allocated (gaps on rollback) — acceptable, but worth a one-line decision-log note since numbering is user-visible. Optimistic concurrency adds a 409 the web client must handle gracefully (a "this changed, reload" rebase prompt). None of the three is glamorous, so it competes for attention against the feature work above — the argument for it is "do it in the same PR as the portal foundation."

Convergence: the numbering fix alone surfaced in 5 of 6 frames; cross-domain added the sequence + idempotency-key framing, pain the concurrency race.
6

Make the export trustworthy: Exported / Not-exported / Drifted badge

Confidence 88% Complexity Low direct trust · cheap win

Description. sheetsSyncedAt is computed, stored, and already in the API payload — but invisible in the UI, so the only way to know whether an invoice reached the tax spreadsheet is to open the database. Add a per-invoice badge with three states borrowed from git's ahead/behind: Not exported (sheetsSyncedAt IS NULL), Exported, and Drifted (updatedAt > sheetsSyncedAt — edited after export, so the sheet is now stale). Pure read-side; respects the one-way export constraint.

Basis · direct
schema.prisma carries both sheetsSyncedAt DateTime? (line 49) and updatedAt DateTime @updatedAt (line 51), so "Drifted" is a free comparison (verified). The field is currently surfaced nowhere — only a comment in useExportInvoices.ts notes it "isn't surfaced in the list/stats today."
Rationale

An at-least-once, fire-and-forget export with no visible confirmation forces the user to distrust it and manually reconcile against Sheets — defeating the point of automating the export at all. The "Drifted" state catches the genuinely dangerous case the export can't see: a landlord edits an amount after exporting and their tax sheet is now silently wrong. Highest value-per-line in the set; the data is already on the wire.

Downsides

"Drifted" is advisory only — the app deliberately won't re-push (DEC-001), so the badge tells the user to re-export manually rather than fixing it, which some will read as the app nagging. Clock-skew edge cases (updatedAt vs sheetsSyncedAt within the same request) need a small tolerance so freshly-exported rows don't flicker "Drifted."

Convergence: 4 of 6 frames; cross-domain contributed the three-state git ahead/behind framing that upgrades it from a binary badge.
7

Finish the two-sided product: a scoped contractor submission portal

Confidence 75% Complexity High direct north star · product expansion

Description. The CONTRACTOR role exists in the enum and drives nothing; the whole app assumes one landlord types every invoice. Make the contractor a real, scoped actor: they sign in, submit invoices with photos, and see only their own submissions and their status — never other contractors' rows, never the approve action. The landlord works a single "needs-me" queue. The existing ownership seam (where:{userId}) generalizes to role-scoped visibility without violating the no-existence-leak rule (DEC-019).

Basis · direct
Role enum in schema.prisma includes CONTRACTOR but no auth/visibility logic references it (grep-confirmed empty). The domain arc in the design doc — "contractor submits → landlord reviews → approves/rejects → pays" — describes a two-actor flow where only one actor was built. External: fleet dispatcher/driver separation, solved with photo-proof = exactly the InvoiceImage feature.
Rationale

This is the single biggest latent product sitting in the codebase: the data model, role enum, status lifecycle, and image relation were all designed for a two-sided flow that was never wired. Without a real second actor, the photo feature, the approval step, and the timeline all lack an audience. It's the destination the other six ideas point at — and it's why ideas 2 (audit), 4 (approval gates), and 5 (concurrency) are worth doing first: they're its load-bearing foundations.

Downsides

Biggest scope and lowest confidence in the set — it's a genuine authorization-model fork (today "the landlord owns all rows" is an implicit invariant; a contractor breaks it), plus registration/invites, role-scoped queries everywhere, and a second UI surface. Should not start until the concurrency hardening (idea 5) and a real event/audit trail (idea 2) exist, or it multiplies writers against unsafe write paths. Best treated as the north star that sequences the rest, not the next PR.

Convergence: 3 of 6 frames (inversion, assumption-breaking, constraint-flip) — the constraint-flip frame named it "the biggest latent product in the codebase."

Grounding Context

Surprise-me run, grounded in the repository. Codebase scan + institutional-decisions search (docs/DECISIONS.md / docs/CONVENTIONS.md) + external prior-art research. A fresh-context verifier checked every load-bearing code citation: 7 sound, 2 weak, 0 refuted.

Codebase Context

  • Shape. TS npm-workspaces monorepo (Node 22): Fastify 5 + Prisma 7 + Postgres API, React 19 + Vite + TanStack Query + RHF + shadcn/ui web, Zod 4 shared schemas. Deployed on Vercel (SPA + /api function, same origin).
  • Works today. Auth (argon2id, rate-limited login), full invoice CRUD, URL-state filter/sort/search, status counts via /stats groupBy, Google Sheets export (one-way, at-least-once, formula-injection-safe), security hardening (helmet, body limit, log redaction).
  • Binding decisions. Postgres is source of truth; Sheets is export-only (two-way sync / Sheets-as-store are rejected, DEC-001). Ownership scoped to session user everywhere (no existence leak, DEC-019). Integrations live behind a thin, mockable, error-sanitizing seam (DEC-022).
  • Known gaps. InvoiceImage modeled but unused; APPROVED has no UI; nextInvoiceNumber full-table scan; mobile nav is logout-only; sheetsSyncedAt invisible; propertyId captured but unfilterable; CONTRACTOR role drives nothing.
  • Users / intent. Landlord-centric "Rent Ops" tool for contractor/vendor invoices. Phase 7 backlog: file attachments (R2/S3), continuous Sheets sync, email reminders (Resend), analytics charts, multi-property, contractor portal, Sentry.

External Context

  • Competitive baseline (FreshBooks/Wave/Zoho/QuickBooks): the gap is the reporting/export layer, not CRUD. Property platforms (Buildium/AppFolio) run a ~9-state lifecycle with a "next owner" per state and auto-generate 1099-NEC.
  • OCR: practical path is an API (Veryfi / Document AI / Textract free tiers), not in-house. IRS Schedule E makes category a tax-line identity; repair-vs-improvement is the most consequential call.
  • Brandur on soft-delete: prefer a separate archive/event record over a deleted_at flag in financial apps. Cross-domain framings: git commit-log for history, accounting journal, medical 7-yr tombstone, fleet dispatch with photo-proof.
