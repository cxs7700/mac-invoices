Grounding Context

Codebase Context. Mac Invoices is an npm-workspaces monorepo: React 19 + Vite + Tailwind CSS v4 + shadcn/ui ("new-york") in apps/web, Fastify + Prisma/Postgres in apps/api. Two personas: a landlord and contractors ("Rent Ops"). The theme infrastructure is half-wired and the grounding turned up unusually concrete evidence:

  • apps/web/src/index.css declares @custom-variant dark (&:is(.dark *)) and 31 light-only CSS color tokens (the documented Rent Ops palette, DEC-017 + docs/design/rent-ops-reference.md), mapped through @theme inline — but no .dark block exists, so toggling the class does nothing today. No toggle UI, no persistence.
  • Preference precedent (locale): localStorage read synchronously at boot (before React renders), User.locale as server source of truth on /api/auth/me, AuthGuard reconciles after the session resolves, and the toggle writes both (localStorage + PATCH /api/settings/profile). LanguageSwitcher is mounted in both the AppShell mobile header and the Sidebar desktop footer with a persist prop.
  • Verified hazards: three hardcoded overlays (bg-black/70 lightbox, bg-black/40 drawer scrim, bg-black/30 confirm scrim), text-white on the destructive button, a hardcoded ::selection, a missing --destructive-foreground token, and zero print styles anywhere. Everything else uses token classes.
  • Invoice photos (cash, parts, checks) are core evidentiary content rendered as <img> in token-colored cards — the one surface CSS tokens can't fix.
  • External: the official shadcn/ui Vite dark-mode guide is a near drop-in for this stack (ThemeProvider, tri-state, localStorage) but omits the inline blocking script that prevents first-paint flash; convention has shifted to three-state light/dark/system controls; WCAG contrast applies identically to dark palettes.
  • Conventions honored: Definition of Done is lint && typecheck && test green (CI-enforced); cost-averse (no paid deps); durable design decisions get DECISIONS.md entries.

1

The zero-FOUC delivery ladder

persistence-first-paintConfidence 85%Complexity Medium
Description
Ship dark mode in three independently shippable rungs, sequenced so the hardest problem (first-paint flash) doesn't exist until the rung that solves it. v0: widen @custom-variant dark to also match prefers-color-scheme: dark and add the .dark token block — dark mode ships with no ThemeProvider, no localStorage, no boot script, and structurally zero FOUC, because media queries resolve before any JavaScript runs. v1: add the tri-state toggle plus a ~10-line inline blocking script in index.html that reads localStorage, resolves system via matchMedia, and sets the .dark class, color-scheme (so native scrollbars, form controls, and the gallery's <select> go dark), and a <meta name="theme-color"> as one unit — fixing the hardcoded ::selection in the same file. Store 'light' | 'dark' | 'system' from the first commit; a boolean is a one-way door that costs a migration later. v2 (optional): the View Transitions circular wipe as polish.
Basis
direct: index.css:4 — class-only variant routing is verified as the sole blocker to a media-query v0; index.html:1–13 — verified bare head (no inline script, no theme meta). external: the inline-blocking-script pattern (notanumber.in; also used by next-themes) is the only reliable SPA fix for first-paint flash, and the shadcn Vite guide omits it.
Rationale
The FOUC axis exists only because a class toggle is assumed from day one. Re-sequencing deletes the risk from v0 entirely and localizes it to v1, where the boot script solves it. Each rung delivers user-visible value on its own, and a stall after any rung still leaves a working feature.
Downsides
v0 gives OS-followers dark mode but offers no manual override, which users who keep their OS dark but want the app light may notice; the variant must be widened carefully so v1's class routing composes with the media query rather than fighting it.

Status pairs as emissive "instrument-cluster lamps"

dark-palette-tokensConfidence 85%Complexity Low
Description
The four status pairs (paid, overdue, pending, submitted) are the app's highest-stakes pixels, and they are constructed as dark-text-on-pale-tint — a construction with no valid naive inversion. Borrow the automotive night-cluster recipe: keep the hue (paid stays green, overdue stays red — semantics constant), swap the luminance roles (a luminous foreground on a low-luminance tinted well), and rank foreground brightness by actionability — overdue brightest, quiescent states sinking toward chrome ("dark cockpit": a calm panel means all is well). Hand-design these 8 values; first-draft the other ~23 chrome tokens with a small OKLCH transform script, then record the resulting palette (or the transform itself) as a DECISIONS.md entry per the DEC-017 convention. Mint the missing --destructive-foreground in the same pass — light mode papers over it with a hardcoded text-white today.
Basis
direct: index.css:72–81 — the four fg/bg pairs verified (--status-paid-foreground: #1f8a5b on #e6f4ec, etc.); ui/button.tsx:14 — text-white with no --destructive-foreground token, verified. external: automotive day/night instrument-cluster convention; WCAG 4.5:1 applies unchanged in dark palettes.
Rationale
A landlord misreading "overdue" as "paid" at 11pm is a correctness bug wearing a cosmetic disguise. One written generation rule produces all ten status values deterministically and gives the DECISIONS entry its rationale for free — while the transform handles the low-stakes chrome tokens mechanically.
Downsides
Hand-designing 8 values plus reviewing ~23 generated ones is real design time; the split approach (hand + script) needs the boundary documented or future tokens won't know which side they're on.

The Theme Integrity Suite

surface-edge-casesConfidence 80%Complexity Medium
Description
One PR that rides the existing Definition-of-Done gates and makes the theme self-enforcing forever. (a) A hand-rolled vitest suite parses index.css, computes WCAG contrast for every declared fg/bg token pair in both theme blocks (4.5:1 normal, 3:1 large/badge), and fails when a :root token is missing from .dark — a check that would have caught the missing --destructive-foreground on day one, and matters because an incomplete .dark block fails silently (unset variables cascade from :root). (b) Close the five known token bypasses — a --overlay token for the two scrims, --destructive-foreground, the ::selection fix, with the lightbox's bg-black/70 kept literal and documented as a deliberate theme-invariant "cinema surface" — then add an ESLint/grep gate banning raw color literals outside index.css.
Basis
direct: all five literals verified at file:line (InvoiceImageGallery.tsx:154, AppShell.tsx:54, InvoiceDetail.tsx:160, button.tsx:14, ::selection in index.css); components.json cssVariables: true means the whole palette lives in one parseable file; CI already gates lint && typecheck && test.
Rationale
Dark-mode bugs in token-based systems come almost exclusively from token bypasses and silent palette drift. Closing the known bypasses and the door they came through converts a one-time styling task into a standing invariant — and it's a model first artifact for the currently empty docs/solutions/ knowledge base.
Downsides
Hand-rolled CSS parsing plus WCAG math is fiddlier than the "~40 lines" it sounds like; the lint rule adds a policy every future frontend PR must obey, which the team should opt into knowingly.

"Paper stays paper": photo mat + forced-light print

surface-edge-casesConfidence 70%Complexity Low
Description
One principle with two instances: surfaces representing physical paper are theme-invariant. (a) A --photo-mat token pinned to the same neutral mid-gray in both themes backs the photo thumbnail wells and the lightbox, so flash-lit photos of cash, checks, and parts read like prints on a mat rather than glaring rectangles floating on near-black — the convention every serious photo tool (Lightroom, gallery apps) converged on. (b) A @media print block re-pins the tokens to light values and hides chrome. Zero print styles exist today; printing is accidentally correct only because :root is light-only — the moment .dark ships, Cmd-P from dark mode produces charcoal invoices, the one dark-mode bug that yields a physically wrong business artifact instead of a cosmetic glitch.
Basis
direct: InvoiceImageGallery.tsx:64–76, 154 verified (thumbnails sit in token-colored bordered cards; lightbox backdrop bg-black/70); repo grep verified zero @media print matches. external: constant-neutral-surround convention in photo tooling; prepress "output intent" separation. Note: the verifier corrected an earlier framing — thumbnails already have a border and padding, so the mat replaces their token-colored backing rather than adding a missing frame.
Rationale
Photos are the one surface tokens can't fix (the pixels are the content), and print is the one surface nobody tests from dark mode until tax season. Both are ~10–20 line fixes if made in the same PR as the palette, and both get expensive as bug reports later. Whatever photo convention ships first will be copied into the still-deferred upload UI and any future export path.
Downsides
A theme-invariant mat is a deliberate exception to "everything themes," which needs a comment or DECISIONS line so a future cleanup doesn't "fix" it; photo-contrast benefit is a design judgment, not measured.

Extract SegmentedSwitcher<T> — the theme control for free

toggle-ux-placementConfidence 85%Complexity Low
Description
LanguageSwitcher is already a generic segmented control: role="group", per-segment aria-pressed, active-state styling, an optional persist prop for server sync, and dual mounts (AppShell mobile header + Sidebar desktop footer). Extract SegmentedSwitcher<T> taking {options, value, onChange, renderLabel}; LanguageSwitcher becomes a thin wrapper, and ThemeSwitcher becomes another — three segments (Sun / Moon / Monitor, tri-state with system default, per current convention), 20×20 inline SVGs matching the NotificationsBell icon pattern, with a test file mirroring LanguageSwitch.test.tsx. The second preference control is where a design system either compounds or forks into near-duplicates; this decides it in the compounding direction at roughly negative net lines of code.
Basis
direct: LanguageSwitcher.tsx, AppShell.tsx:24–50, Sidebar.tsx:26–38 all verified verbatim, including the aria-pressed/role="group"/persist structure. external: three-state light/dark/system with a Monitor icon is the prevailing convention.
Rationale
The app already solved "compact preference switcher living in two chrome locations with optional server sync" once. Cloning the pattern by extraction (rather than copy-paste) means the third preference control — and the review checklist for it — is nearly automatic.
Downsides
A settings-page-only placement (rejected below) would avoid adding a fourth control to already-crowded chrome; if chrome load becomes a concern, the extraction still pays off wherever the control lands. Classic second-instance abstraction risk: two instances may not yet reveal the right generic API.
6

Decide the persistence fork on purpose

persistence-first-paintConfidence 75%Complexity Low
Description
The single biggest scope fork in the feature, worth an explicit decision rather than a default. Option A — device-local: localStorage only. Theme is arguably device state (like OS appearance), and this skips five moving parts: the User.theme column and migration, the Zod schema change, the PATCH plumbing, the query invalidation, and the reconcile effect — each a place a bug can live. Option B — preference primitive: clone the locale rails (User.theme, /me, PATCH /api/settings/profile), formalizing a twice-proven template any future per-user preference reuses nearly for free. Either way, one corrected hazard stands: if server sync ships, the post-login reconcile must never visibly repaint the app — apply the server value silently or before paint, rather than copying AuthGuard's visible-after-resolve pattern verbatim.
Basis
direct: AuthGuard.tsx:18–25 reconcile effect, settings handlers, and schema.prisma locale field all verified. reasoned: the cost delta between the options is measured in actual files touched, enumerated from the locale implementation. (The verifier rejected an earlier premise that locale's reconcile was "imperceptible" — a full text-language swap is plenty visible — so the hazard is stated on its own merits, not by contrast with locale.)
Rationale
This choice determines the schema, the API surface, and the switcher component's props before any code lands. Deciding it explicitly is cheap; un-deciding a shipped User.theme column or retrofitting sync later is not.
Downsides
Option A gives up cross-device continuity (landlord's phone vs desktop); Option B commits future preferences to the same shape and adds a migration to this feature's scope.
A · Device-local
  • localStorage only; no schema, API, or migration changes
  • Five fewer moving parts, five fewer bug surfaces
  • No cross-device continuity
B · Preference primitive
  • User.theme + /me + PATCH, on the proven locale rails
  • Formalizes the template for every future preference
  • Must reconcile silently — never a visible post-login repaint

Role-aware default: contractors get light

persistence-first-paintConfidence 55%Complexity Low
Description
"System default" is generic-webapp dogma; this app has exactly two user archetypes with opposite lighting contexts, and the server already knows which one is logged in. Contractors work phones outdoors in daylight, where a scheduled OS dark mode produces a glare-unreadable UI at exactly the wrong moment; the landlord does books indoors, where following the system is right. Resolution order: explicit user choice > role-based default (CONTRACTOR → light, others → system) > light for pre-auth screens.
Basis
direct: useAuth.ts:5 — role is on the auth payload, verified. reasoned: outdoor-glare legibility is a well-established UX claim — but the persona inference is not backed by usage data, so confidence is deliberately low.
Rationale
A one-line default rule that serves the app's second persona better than the imported consumer-app convention — and it composes with any of the ideas above (it only changes what system resolves to before an explicit choice exists).
Downsides
Speculative until a contractor actually complains or is asked; role-dependent defaults are a small surprise ("why does my app ignore my phone's dark mode?") that must be easy to override.
