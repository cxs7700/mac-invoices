Grounding Context

Codebase Context

Shape

  • npm-workspaces monorepo: React 19 + Vite web, Fastify 5 API, shared Zod schemas. Postgres + Prisma, Node 24.
  • One landlord, multiple properties. Vendors submit via no-login HMAC-token links; the landlord reviews, approves, pays.
  • Reporting surfaces today: the dashboard, the invoice list, a Google Sheets mirror, and a client-side per-invoice PDF.

Settled decisions the ideas must respect

  • Filter/sort/page state lives in the URL, never component state; aggregates get their own endpoint (DEC-020, CONV-015).
  • DateRangePicker and parseListParams were deliberately extracted so the list and dashboard share one control, one parser, the same URL keys.
  • Charts are hand-rolled flex DOM — no chart library in any package.json. jsPDF was accepted at ~137 KB gz only behind a dynamic import().
  • Money is Decimal(10,2), serialized as a string, never float math.
  • Ordering across four surfaces delegates to one shared natural-order comparator, because invoiceNumber is a nullable string.

Gaps found during grounding

  • No period-over-period comparison exists anywhere, despite five years of data (2021-02-05 → 2025-12-23).
  • No aging or days-outstanding logic exists anywhere.
  • No per-vendor spend rollup exists at all; the only _sum is on Property.
  • No CSV export exists anywhere outside the seed loader.
  • The reporting surface was never designed — the Rent Ops design reference lists "dashboards, report builder, Sheets/PDF/Excel export" under Deferred.

External context

  • Buildium, AppFolio and Yardi generate automated owner statements; Buildium splits reporting into three report families rather than one dashboard.
  • Stessa frames the dashboard around investor metrics (NOI, cash-on-cash) plus a portfolio asset register.
  • Baselane maps 120+ categories directly onto Schedule E lines — the tax form built into the taxonomy, not bolted on as a report.
  • Every reviewed vendor treats Schedule E mapping as table stakes; all are criticised as overkill below ~50 units.
  • The 1099-NEC threshold is mid-flight regulation: historically $600, raised to $2,000 for 2026 under OBBBA.
  • YNAB vs Mint is the canonical contrast for a dashboard that changes behaviour versus one that displays.

Topic Axes

  1. At-a-glance dashboard at-a-glance-dashboard — what the landing view shows and what decision it drives.
  2. Invoice list as a working surface invoice-list — filter, sort, search, bulk, aging.

1

Make every figure trustworthy: one spend definition, one primitive

at-a-glance-dashboard Confidence 92% Complexity Medium
Description

The app currently holds at least two different answers to "what counts as spend," computed in two places, and shows them without saying which is which. Unify them behind one extracted spendReport(where, groupBy) primitive that owns the status rule, move the outstanding total off parseFloat and onto Decimal.add, and give every reporting surface a shared scope banner that states its window and its status filter in words. Where a figure excludes rows, show the excluded residual as a labelled band rather than dropping it silently.

Axis
at-a-glance-dashboard
Basis

direct: The dashboard's spend filters status: { notIn: ['SUBMITTED','REJECTED','CANCELLED'] } (apps/api/src/invoices/handlers.ts:244), while a property's totalSpend excludes only REJECTED/CANCELLED (apps/api/src/properties/handlers.ts:67). Two divergent definitions, both called spend.

direct: The handler's own comment states that excluding those statuses "keeps byCategory reconciled with the total… no stray null-category bucket" (handlers.ts:231-236) — the reconciliation is achieved by hiding the residual.

direct: Dashboard.tsx:74 derives outstanding with parseFloat(s.amount) on Decimal strings, which the project's own money convention warns against extending into an authoritative figure.

direct: Verification correction — the list's status strip carries no scope label at all, while the dashboard has an explicit dashboard.allTime string. The mismatch is worse than "two labels that read alike": one surface is labelled and the other simply isn't.

Rationale

Every other idea in this document puts more numbers on more screens. None of them survives a landlord noticing that two screens disagree and neither says why. This is the prerequisite: it converts a silent, undocumented inconsistency into either one number or one clearly-stated distinction, and it extracts the primitive that the vendor and property rollups downstream would otherwise each re-derive — correctly or not.

Downsides

The two definitions may both be right for their context, in which case unification is the wrong move and labelling is the whole job — that call has to be made deliberately rather than assumed. A visible residual band adds a second number to a surface whose problem is already too many numbers. Extracting the primitive touches the one handler that everything reads from, so it wants tests before it wants a refactor.

Comparison as a seam, with a seasonal band instead of a naive delta

time-and-comparison Confidence 88% Complexity Medium
Description

Add a compare parameter to the shared DateRangePicker / parseListParams URL contract so period-over-period is a property of the seam rather than a feature of one page — every present and future report surface inherits it. Then make the statistic the right one: instead of a year-over-year delta, draw a band derived from the same calendar month across several prior years, and flag only months that fall outside it. Add closed tax-year presets (range=ty2025) alongside the existing open-ended lookbacks, since a completed calendar year is the one period a landlord must report on and currently the one they cannot ask for.

Axis
time-and-comparison
Basis

direct: No period-over-period comparison exists anywhere in the product; byMonth is the only temporal dimension in the summary response.

direct: rangeStart(preset, today) computes preset boundaries purely from today (apps/web/src/lib/listParams.ts:44), so deriving a shifted comparison window is a local change to a function that already does exactly this arithmetic.

direct: Presets deliberately leave to open — they mean "since X" (listParams.ts:41-43) — and ytd is the only calendar-anchored option, always meaning the current year. Five tax years sit in the data and none is directly addressable.

direct: The seed data spans 2021-02-05 to 2025-12-23 — five complete seasonal cycles, enough for a band to mean something.

reasoned: At single-landlord volume a naive year-over-year delta is actively misleading: one $4,000 roof in March 2025 makes March 2026 read as a 90% improvement. A band built from several prior years is robust to exactly that single-event distortion, which is why epidemiological surveillance uses a seasonal threshold rather than last-year-same-week.

Rationale

A spend figure with no reference point cannot be acted on — "$4,200 this quarter" only becomes a decision once it is "$4,200, well outside the usual range for this quarter." Building comparison into the shared URL contract rather than into the dashboard component is what turns it from one feature into a capability every later surface gets for free, and it follows the precedent the team already set when it extracted the date picker so the two pages could not drift.

Downsides

A second series is the moment the no-chart-library decision gets re-litigated: SpendTrendChart is flex-laid-out DOM with one hue and no legend precisely so it stays readable without measuring the DOM, and it already thins month labels at nine buckets and again at seventeen. A band plus bars plus a flag may not survive that constraint, and finding out is part of the work. The band is also only as good as the history behind it — the first two years of any property produce a band nobody should trust, so it needs an honest "not enough history" state.

Priors at the approve moment

invoice-list Confidence 90% Complexity Low
Description

When the landlord opens a submitted invoice to approve it, that vendor's prior invoices for the same property and category are already on screen — "last three drain calls at 5th Street: $220, $195, $840." No search, no filter, no second page. The comparison is retrieved because a decision is being made, not because the landlord thought to go looking for it.

The mechanism is borrowed from radiology: a PACS workstation never shows a study cold, because the hanging protocol auto-retrieves the patient's prior scans and hangs them adjacent — in imaging the finding is usually change, not the current image. The same holds for judging whether an invoice is reasonable.

Axis
invoice-list
Basis

direct: Both vendor relations are already included in listInclude and returned on every list row (apps/api/src/invoices/handlers.ts:73-74) — the prior set is one existing query away, not new infrastructure.

direct: The vendor filter is free-text contains and DEC-020(d) explicitly defers a structured vendor picker, so answering "what has this vendor charged before?" today means typing a name into a debounced text box and hoping the spelling matches.

reasoned: The YNAB comparison that dominates this domain prescribes forcing an assignment at the moment of spend. That is the wrong mechanism here: the landlord is not allocating a budget, they are judging whether a number is reasonable, and reasonableness is only assessable against priors. Retrieval, not assignment, is the move.

Rationale

This is the cheapest idea in the set and it lands on the only moment where money is actually committed. The verification pass singled it out as the best-evidenced candidate here — the data is already fetched, so the work is almost entirely presentation. It also reframes the reporting surface usefully: the highest-leverage report may not be a page the landlord visits at all, but three seconds of context before an approve click.

Downsides

Priors are only meaningful when there are enough of them; a first-time vendor or a one-off category shows an empty panel that costs screen space and teaches the landlord to ignore the region. "Same property and category" may also be too narrow a match for a small portfolio — loosening it risks comparing a drain call to a repaint. And an anchoring effect cuts both ways: showing three cheap priors next to a legitimately expensive job invites the wrong pushback.

The tax-year handoff

reports-out Confidence 78% Complexity High
Description

Treat the annual accountant handoff as one designed product rather than four missing pieces. Give the shared category enum a Schedule E line mapping and an orthogonal expense-versus-capitalize dimension, both decided in the approve flow where the landlord is already being forced to pick a category. Generate a tax-year packet from that: a Schedule E-grouped expense summary, the supporting invoice ledger, and the receipt photos. Include an explicit exclusions log naming every invoice deliberately left out and why. Deliver it as a revocable, read-only, tax-year-scoped link — the same HMAC token machinery already built and reviewed for vendors.

The exclusions log is borrowed from legal discovery, where a production is accompanied by a privilege log listing what was withheld, because a silent omission is worse than a disclosed one. This app has an unusually rich set of deliberate exclusions to declare.

Axis
reports-out
Basis

direct: InvoiceCategory is flat and tax-agnostic — MAINTENANCE / REPAIRS / UTILITIES / SUPPLIES / LABOR / OTHER (apps/api/prisma/schema.prisma:316-323) — and is a single shared Zod enum consumed by the dashboard breakdown, the Sheets column and the PDF alike, so mapping it once upgrades every consumer.

direct: Both category and propertyId are already required to transition an invoice to APPROVED (apps/api/src/invoices/writeService.ts:110-134) — the forced-decision moment this idea needs already exists.

direct: EXPORT_COLUMNS omits vendor name and id entirely, with the comment that they are "internal-only and never exported" (apps/api/src/invoices/sheetRows.ts:13-23) — the only structured export excludes the exact field a 1099-NEC requires. There is no CSV anywhere and no dashboard-level PDF.

direct: The vendor link secret is derived, never stored — HMAC(VENDOR_LINK_KEY, tokenLookupId:tokenVersion), rotated by tokenVersion, switched off by revokedAt (DEC-034) — a reviewed pattern a read-only audience can reuse.

external: Baselane maps 120+ categories directly onto Schedule E lines; every reviewed competitor treats that mapping as table stakes rather than a report. The $2,500 de minimis safe harbour makes the capital-versus-repair call a threshold test the app has the data to apply.

Rationale

This is the highest-stakes, lowest-frequency task the landlord performs, and the reporting surface currently cannot help with any part of it: the Sheets mirror is disposable and clear-and-rewritten, the PDF is per-invoice, and neither carries the vendor identity the tax forms are keyed on. Deciding the taxonomy once, in a shared enum, at a moment the landlord is already stopped, is drastically cheaper than reconstructing it from a stack of receipts in April.

Downsides

By far the largest item here, and the only one that is partly a tax-compliance product rather than a reporting one. A category remap is a schema migration touching every consumer and every historical row, and it is close to a one-way door. Getting the capital-versus-repair heuristic wrong is worse than not offering it — a confidently mislabelled improvement is a real tax exposure, so it has to read as a prompt, not a determination. And a read-only external link is a new security boundary on data that includes photographs of the landlord's properties, which deserves its own review rather than an assumption that the vendor pattern transfers.

Vendor spend, forward-projected against the 1099 threshold

vendor-property-rollups Confidence 85% Complexity Medium
Description

Give the vendor rollup the one thing it does not have — money. Then do not stop at a year-to-date total: extrapolate each vendor's own run rate forward and raise the flag when the projection crosses the reporting threshold, not when the actual total does. The threshold is a configurable number, not a literal, because it is mid-flight regulation.

The mechanism is air-traffic conflict alerting: controllers are not warned when two aircraft are close, they are warned when extrapolated tracks predict a loss of separation, because by the time the conflict is visible the cheap remedies are gone. A W-9 is easy to collect in March from a contractor still working for you and hard to collect in January from one who has moved on.

Axis
vendor-property-rollups
Basis

direct: No per-vendor spend rollup exists anywhere in the codebase. The vendor list exposes exactly propertyCount and lastUsedAt (apps/api/src/vendors/handlers.ts:49-50) — a vendor reports how many properties and when it was last used, and no money at all.

direct: The only _sum aggregate in the codebase is on Property. Meanwhile Invoice.vendorId (attribution, deliberately kept distinct from submittedByVendorId per DEC-032), Decimal amounts and invoiceDate are all present — every input the rollup needs already exists.

direct: The Sheets mirror never exports vendor name or id, so the one artifact leaving the app cannot answer a vendor-keyed question at all.

external: The 1099-NEC threshold is genuinely in flux — historically $600, raised to $2,000 for 2026 under OBBBA — which is itself the argument for a configurable line on a chart rather than a constant in a conditional.

Rationale

The app models vendors richly — two foreign keys, a join table, HMAC submission links — and then reports nothing about what they cost. This is the one missing rollup with a statutory deadline attached, and the deadline lands after the data is complete, which is precisely the class of problem forward projection exists for. It also makes the difference between a dashboard that describes and one that prompts.

Downsides

Run-rate extrapolation is unstable on small numbers: a vendor with two invoices in February projects wildly, and a false "about to cross" alert erodes trust faster than no alert. It needs a minimum-history gate and a visible confidence range. There is also a real question of how far the product should go toward asserting a tax obligation versus simply reporting a number — the safest version states the fact and the threshold and lets the landlord draw the conclusion. Depends on the vendor spend rollup from idea 1's primitive to avoid inventing a third definition of spend.

The dashboard as a triage queue, not a spend report

at-a-glance-dashboard Confidence 82% Complexity Medium
Description

Reframe the landing view from "what did I spend" to "what needs me." Score each open invoice from a handful of binned signals — days waiting, amount against that vendor's own norm, missing property, missing category, first-time vendor — and show the score as an ordered queue with each contributing bin visible as a chip on the row. Spend charts move below. Once a year the same machinery runs as a completeness sweep: uncategorised, unassigned, approved-but-never-paid, no receipt attached — each one a filtered link with a bulk fix.

The scoring mechanism is NEWS2, the hospital early-warning score: several routine observations, each binned into points, summed into one number that maps to a mandated action and a re-check interval. Its value is not precision — it is that the absence of attention becomes visible.

Axis
at-a-glance-dashboard
Basis

direct: Zero aging or days-outstanding logic exists anywhere in the codebase — confirmed by search, not inference.

direct: The sortable fields are exactly ['invoiceNumber','invoiceDate','amount','status'] (packages/shared/src/schemas/invoice.ts:138). Submission recency is not among them, so "what has been sitting longest" is not expressible as a sort at all.

direct: Both propertyId and category are required to approve, so an invoice can sit in a state where approval is structurally impossible and nothing on the list says so — "blocked" is already computable.

direct: propertyId=none is already handled in the list query language, and imageCount already rides on the list response via a cheap _count — so "unassigned" and "no receipt" are free signals today.

direct: The handler comment states plainly that byStatus keeps every status because its SUBMITTED count "is the landlord's 'to review' signal" — the intent is already there, buried inside a bar chart.

Rationale

The single landlord using this opens it to decide something, and the four tiles they land on are all retrospective totals. The gap between a count and a queue is the gap between knowing twelve invoices need review and knowing which one has been waiting six weeks and cannot be approved anyway. The NEWS2 borrow specifically avoids an opaque smart score: every contributing bin is displayed, so the score explains itself and the landlord can disagree with it.

Downsides

Choosing the bins is a product argument, not a technical one, and bad bins produce a confidently-ranked queue that is worse than an unranked list. There is a real risk of building a second scoring system nobody tunes. Demoting the spend charts is also a genuine bet — the landlord may in fact open this to check spend, and the only way to know is to ask them. The annual sweep is what justifies building bulk actions, which do not exist at all today.

An outbound delivery board

reports-out Confidence 86% Complexity Low–Medium
Description

One panel that states, per outbound channel, when it last succeeded, how much it delivered, and any exception code. Package tracking's real innovation was never the map — it was that a failed delivery becomes a dated, coded exception scan on the tracking page instead of a parcel that quietly stops moving. Every outbound artifact in this app currently fails silently, and it has done so three separate times.

Axis
reports-out
Basis

direct: RESEND_API_KEY is unset in production, so sendEmail() throws EMAIL_NOT_CONFIGURED and the catch block increments a failure counter and moves on (DEC-036(a)). Production email — digests included — silently no-ops today.

direct: DEC-038: stamping sheetsSyncedAt through Prisma bumped @updatedAt and marked every landlord permanently dirty, masked for months by a 2-second "drift tolerance" that was absorbing a data bug rather than clock skew.

direct: The GitHub Actions sync cron can lag by hours, which is a known and accepted condition rather than a monitored one.

direct: DEC-040's logging allow-list already forbids amounts, names and error messages, leaving stable error codes as the only available vocabulary — which is exactly what an exception code is. The constraint and the design agree.

Rationale

Three independent silent-failure incidents on one surface is a pattern, not bad luck. The existing per-invoice sync badge deliberately collapses three states into Yes/No because at row level only one question matters; that decision is right, and it is also why nothing in the product reports channel health. This is the cheapest way to stop the next months-long silent failure, and it is the only idea here that addresses a live production defect rather than a missing feature.

Downsides

Observability that nobody looks at is just another panel. For a single-landlord app the honest version may be smaller than a board — a single line that appears only when something is wrong. It also risks exposing internal plumbing to a user who cannot act on it: "SHEETS_TABLE_RESIZE_FAILED" is a developer's sentence, and translating codes into landlord-legible states is most of the design work. And it does not fix the email configuration, which is a separate, prior task.
